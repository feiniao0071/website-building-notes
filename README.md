# 从零到长期运行：个人网站搭建经验

建站过程复盘与可复用操作思路

这次建站经历了需求确认、本机开发、云服务器部署、域名购买与解析、HTTPS 配置，以及后续维护。本文整理其中可以复用的经验，供以后搭建小型网站时参考。示例统一使用保留域名和示例 IP，不包含实际网站主题、页面内容、业务数据或登录凭据。

## 一、先把“长期使用”说清楚

开始开发前，先明确网站给谁用、主要从什么设备打开、是否需要修改并保存数据，以及是否需要长期在线。这些条件会影响服务器、数据库和登录方式的选择。

本机开发适合检查界面和功能。网站部署到云服务器后，运行依赖的是云服务器；只要云服务器正常运行，个人电脑关机也不会直接导致网站下线。管理网站的电脑和承载网站的服务器，是两台不同的设备。

如果希望在不同设备上看到同一份最新数据，就需要把数据保存到服务器。仅存在某个浏览器里的内容，通常不会自动出现在另一台设备上。

这次比较有效的推进顺序是：先完成可运行的版本，确认基本操作，再部署到云端，最后完善正式域名、HTTPS、备份和交付说明。界面调整可以继续迭代，但数据保存和访问方式应尽早确定。

## 二、购买前，分清几样东西各自负责什么

| 名称 | 作用 | 容易混淆的地方 |
| --- | --- | --- |
| 云服务器 | 持续运行网站程序，保存应用数据 | 买了服务器，还需要部署程序和配置网络 |
| 域名 | 提供容易记忆的网址，例如 example.com | 域名需要续费，也需要解析到承载网站的服务 |
| DNS 解析 | 告诉访问者这个域名对应哪个地址 | 添加解析记录以后，服务器仍需识别该域名 |
| HTTPS 证书 | 加密浏览器与网站之间的连接，并验证域名对应的服务器身份 | HTTPS 不能代替登录和数据访问权限 |
| 域名实名认证 | 核验域名注册者身份，按注册商要求完成 | 与网站 ICP 备案是不同流程 |
| ICP 备案 | 中国大陆网站接入中的备案手续 | 是否需要与接入资源和服务情况有关，不能只看域名后缀 |

一次访问的大致过程是：浏览器输入域名 → DNS 查到服务器地址 → 建立 HTTPS 连接 → 网站处理请求 → 返回页面或数据。

## 三、服务器的地域，应该在购买前确认

这次遇到的一个实际问题是：已有服务器位于中国香港，进入备案流程后，控制台提示该资源不能用于中国大陆 ICP 备案。

这个提示反映的是资源地域和备案接入条件。继续使用香港服务器，一般无需办理中国大陆的网站 ICP 备案；如果选择中国大陆服务器，则应按接入商要求完成相应备案后上线。域名在国内购买，也不等于网站必须部署在大陆。

| 选择 | 主要考虑 |
| --- | --- |
| 中国大陆服务器 | 适合重点服务大陆访问者，需考虑备案条件和办理时间 |
| 中国香港等非大陆服务器 | 一般无需大陆网站 ICP 备案，访问体验要实测跨境线路 |

不能仅凭“香港”或“大陆”两个标签判断实际速度。用户的运营商、所在地区、服务器线路、带宽、页面大小，都会影响体验。正式使用前，应分别用常用 Wi-Fi 和手机流量打开页面，检查首次加载和日常操作。

如果网站运行正常，也没有转到大陆服务器的明确需求，可以先保留现有资源。遇到备案提示时，先确认地域与接入要求，再决定是否迁移。

## 四、小型网站的配置，从实际需求起步

这次采用了轻量应用服务器、Ubuntu 24.04 LTS 和 x86_64 架构，起步配置为 2 核 CPU、2 GB 内存和 40 GB 云盘。这样的规格可以作为轻量应用的起点，但不能据此保证任意网站或任意访问量都够用。

选购时，除了 CPU 和内存，还应看清公网带宽、流量额度、超额计费方式、磁盘大小，以及续费价格。大量图片、视频、复杂后台任务或者访问量增长，都可能需要重新评估资源。

几个数字可以这样理解：

- CPU 影响程序处理请求和任务的能力。
- 内存是程序运行时使用的空间，不是文件存储容量。
- 云盘保存系统、代码、数据库、上传文件和日志。
- 带宽和流量影响数据传输，不能与内存、云盘混为一谈。

例如，购买 40 GB 云盘后看到只剩约 33 GB 可用，通常是系统和已安装软件占用了部分空间。这个数字表示当前可用磁盘容量，不能直接换算成网站还能服务多久或能接待多少人。

## 五、域名先买一个，注意续费价格

购买 example.com，并不要求同时购买 example.cn 或 example.cloud。不同后缀是独立的域名，多个后缀通常用于品牌保护或不同用途。普通个人项目先选一个合适的主域名即可。

拥有 example.com 后，可以在自己控制的 DNS 中添加 www.example.com、app.example.com 等子域名，通常无需再为这些子域名支付注册费；它们使用的服务器或其他服务仍可能产生费用。

购买时最值得检查的是：

- 名称是否容易记、容易输入，拼写是否正确。
- 首年价格和续费价格分别是多少。
- 账号是否由自己掌握，联系邮箱能否收到通知。
- 域名实名认证是否完成。
- 订单中是否勾选了并不需要的附加服务。

## 六、域名解析是一张地址表

把域名指向服务器时，最常见的是 A 记录，用来关联一个 IPv4 地址。下面仅演示字段含义，不能直接复制到真实网站：

| 主机记录 | 记录类型 | 示例记录值 |
| --- | --- | --- |
| @ | A | 203.0.113.10 |
| www | A | 203.0.113.10 |

其中，@ 表示根域名 example.com，www 表示 www.example.com。203.0.113.10 是文档专用的示例地址，实际操作必须替换成自己的服务器公网 IPv4。

如果控制台提供“新手快速解析”，通常可以同时勾选根域名与 www，填入同一个服务器 IP，一次生成两条记录。线路和 TTL 没有特殊要求时可以先保留默认值。TTL 与解析缓存有关，修改后的结果可能不会同时出现在所有网络中。

保存成功表示平台接受了配置。接下来还要查询实际 DNS 结果，确认地址正确。如果该域名本来已经在使用，添加前应先检查已有记录，避免留下冲突或错误的旧地址。

## 七、域名解析之后，还要完成服务器和 HTTPS 配置

这次正式上线使用 Docker Compose 管理应用与反向代理，由 Caddy 处理 HTTPS。反向代理接收浏览器请求，再转给内部运行的应用。

切换到正式域名时，实际需要完成以下几件事：

1. 核对根域名与 www 的解析结果。
2. 让服务器的代理配置识别新域名，并转发到正确应用。
3. 同步修改应用自己的正式访问地址配置。
4. 确认云防火墙、系统防火墙及服务监听允许所需的 HTTP/HTTPS 访问。
5. 申请证书，核对浏览器是否信任，再检查自动续期配置。
6. 确定唯一的主域名，把其他入口统一跳转过去。

第三步很容易漏掉。某些应用会用正式地址生成链接、校验请求来源。只改 DNS 或代理配置，可能出现首页能打开，但登录、提交或分享链接不正常的情况。

Caddy 可以在条件满足时自动申请和续期受信任的证书。通常不必因为网站需要 HTTPS 就购买付费证书，但应保留证书存储，并持续满足续期所需的域名和网络条件。

这次也曾先使用 IP 地址提供 HTTPS，之后再绑定域名。IP 证书需要客户端和证书机构支持，维护条件可能与普通域名证书不同。新项目若已确定长期使用，尽早准备域名，可以减少一次访问入口切换。

## 八、换网址时，把数据、登录状态和旧链接分别检查

域名切换涉及的不只是网址。此次操作前先备份配置和数据，再启用新配置，并对切换前后的业务数据进行核对。

应用代码、环境配置和数据库应分别管理。重新部署代码时，继续挂载原来的持久化数据；不能把开发电脑上的初始数据直接覆盖线上数据库。Docker 容器可以重建，持久化数据卷需要保留。尤其不要误用会删除数据卷的命令，例如 docker compose down -v。

浏览器把不同域名或 IP 视为不同站点。因此，即使服务器数据完全保留，换域名后也可能需要重新登录。旧站点的 Cookie 和浏览器本地草稿，不会因为设置了跳转就自动迁移。

旧链接兼容需要实际点击验证，包括路径、查询参数，以及应用使用的链接片段。重定向不会把旧站点的登录状态转移到新站点；验收时应分别确认跳转正确和新站点登录成功。

## 九、上线验收，要走一遍真实操作

“部署命令成功”“容器正在运行”“首页能打开”分别证明了不同事情。完整验收应沿着用户实际使用路径继续检查。

这次采用的核验思路可以复用：

- 访问：域名解析正确，HTTPS 受信任，其他入口跳转到主域名。
- 身份：需要登录的数据在未登录时不能读取，不同身份能进入正确的访问范围。
- 操作：常用页面和数据操作可以完成，刷新后结果仍然存在。
- 手机：常见屏幕宽度下能看清内容、点到按钮，没有意外横向溢出。
- 持久化：服务重启后，已保存的数据仍在。
- 变更核对：修改域名或配置以后，已有数据没有被替换或重置。

手机尺寸模拟能发现布局问题，但无法完全代表真实手机、微信内置浏览器或蜂窝网络的表现。验收记录应注明哪些已经实测、哪些只做了模拟、哪些仍待检查。

正式数据已经有人使用后，测试操作应控制范围。优先检查现有数据的读取和界面；确实需要写入测试数据时，应明确标记并清理，避免混入日常内容。

## 十、长期维护：自动运行、定期检查与故障恢复

长期维护需要有明确的执行机制、检查周期和恢复办法。下面把已经配置的部分与后续建议分开记录；维护结果应有日志、备份文件或实际操作作为依据。

### 10.1 已经配置的自动机制

- 服务运行：容器异常退出后按重启策略尝试恢复；服务器正常启动后，服务随容器运行环境启动。主动停止的服务不会因此自动恢复，持续性程序错误仍需处理。
- HTTPS：由代理服务管理证书并自动续期，需要持续满足证书机构的验证条件，并保留证书存储。
- 数据备份：每天定时备份，核对数据库完整性及关联文件，保留最近 7 份已完成快照。
- 备份空间：按保留策略清理旧的已完成快照，失败批次不会替换之前的完整备份。

本次核验确认：定时任务处于启用状态，最近一次定时备份执行成功，应用与代理容器均在运行。上述机制可以减少日常操作，但仍需要检查它们有没有持续正常工作。

### 10.2 建议采用的维护节奏

下表是建议安排，尚未创建自动巡检任务或日历提醒。可根据使用频率调整，并指定由谁负责。

| 频率 | 具体检查 | 留下什么记录 |
| --- | --- | --- |
| 每周一次 | 打开网站并登录，完成一次常用操作；检查最近备份是否按时产生 | 检查时间、操作结果、最近备份时间 |
| 每月一次 | 检查磁盘和流量用量、证书有效期、服务器与域名到期日；评估系统和依赖更新 | 剩余资源、到期日、需要处理的更新 |
| 每次发布前后 | 发布前备份并保存旧配置；发布后验证访问、登录、主要操作及数据保留 | 版本、变更内容、验证结果和回退位置 |
| 每季度或重大改动后 | 在临时环境中，用一份备份恢复并检查数据；记录恢复耗时 | 使用哪份备份、是否完整、恢复步骤和耗时 |

### 10.3 更新网站时，维护动作怎么执行

把代码、配置和业务数据分别管理。更新前备份数据并保留上一版代码、镜像或配置；先检查新配置，再按应用需要重新加载或重建服务。更新后核对功能和数据，记录是否可以回退。

故障如果由代码或配置更新引起，优先评估回退对应版本。恢复业务数据要单独判断，并先保留当前数据，防止用旧备份覆盖发布后已经产生的新内容。部署时继续使用持久化数据卷，避免误用会删除数据卷的命令。

### 10.4 出现故障后，按什么顺序恢复

1. 记录出问题的时间、表现和最近变更，检查域名解析、证书、服务器、应用进程及磁盘状态。
2. 按查到的原因修复配置、恢复服务或回退版本，保留相关日志。
3. 确认需要恢复数据时，先另存当前数据，再选用经过完整性检查的备份，先在临时环境核验。
4. 恢复后重新检查登录、常用操作和数据，并记录恢复到哪个时间点、哪些变更可能未包含在备份中。

每日备份意味着最新备份之后的修改可能无法通过该备份找回。最近 7 份快照也不一定覆盖完整 7 天，手工备份会增加快照数量。恢复能力要靠实际演练确认；目前没有给出经过测量的恢复时长承诺。

### 10.5 后续需要补齐的维护能力

- 自动异地备份：目前有同机定时备份和人工留存的本地副本，尚未配置自动异地备份。同一块服务器磁盘损坏时，同机副本也可能受影响。
- 故障自动通知：当前没有已验证的网站不可用、备份失败或空间不足自动通知机制；需要另行配置监测方式、通知渠道和接收人。
- 续费管理：服务器和域名分别核对到期日、自动续费开关和支付条件，不能把证书自动续期当作资源已经续费。续费提醒仍需落实。
- 定期恢复演练：已有备份完整性检查，后续还应验证从备份恢复到可使用状态的完整流程，并保存操作记录。

维护记录可以固定为：检查日期、检查人、网站与资源状态、最近备份、到期事项、本次变更、发现的问题、处理结果。普通经验文档继续使用占位符，实际运维地址与凭据另行保管。

## 十一、下次可以直接复用的执行顺序

1. 明确主要访问设备、数据保存需求和长期运行要求。
2. 先选服务器地域，弄清备案与网络取舍，再购买资源。
3. 完成本机版本，把代码、配置和数据分开管理。
4. 部署到服务器，核对基本访问、登录和数据持久化。
5. 购买一个主域名，完成实名认证，配置 DNS。
6. 更新服务器域名配置和应用正式地址，启用 HTTPS。
7. 验证新旧入口、真实操作和手机体验，记录尚未实测的部分。
8. 配置备份与恢复、续费提醒，保存维护说明。

让技术协作者或 AI 助手执行时，可以一次说明清楚：“沿用已有资源，变更前备份，保留线上数据；完成后给出访问入口、验证结果、未完成项和恢复方法。”付款、实名认证和扫码登录等需要本人操作的环节，与程序部署、配置检查等技术工作分开推进，沟通会更顺畅。
